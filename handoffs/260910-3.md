## 1. A frente 7 — adapter-parity

Criada porque a mudança da 7.1 **não cabia** nas frentes existentes:

- **Frente 5 (refactorings)** tem por critério *"nada mudou"*. Somar
  `put/remove/all/flush` ADICIONA comportamento — não é refactor.
- **Frente 6 (fswatch)** é *evidência sobre o iodb a partir de um consumidor*. A 7.1
  é mudança do ENGINE, não do fswatch.
- O alvo natural — *"todo adapter do iodb responde à mesma interface chaveada"* — é
  uma propriedade do conjunto de adapters, e é maior que sqlite.

`plans/7-adapter-parity/_front.md` carrega a tese. **NÃO cobre**: os outros adapters
(`folder`, `file`, `jsonl`, `yaml`, `json`, `env` — cada um vira feature própria da
frente 7), um seletor de backend unificado no `db-factory.js`, e performance (isso é
a 6.3).

### 7.1 — o que foi feito

`src/adapters/sqlite.js`: `SqliteCollection(file, { table })` agora tem, ALÉM do
passthrough intacto:

| iodb `IO(merge)`         | `SqliteCollection({ table })`                       |
|--------------------------|---------------------------------------------------|
| `io.in({ [id]: row })`   | `put(id, row)` → `INSERT … ON CONFLICT(id) DO UPDATE` |
| `io.in({ [id]: null })`  | `remove(id)` → `DELETE FROM {t} WHERE id = ?`      |
| `Object.values(get('#1'))` | `all()` → `SELECT * FROM {t}`                    |
| `io.flush()`             | `flush()` → no-op (SQLite já é durável por statement) |

`in(patch)` reconhece a forma keyed (`{ [id]: row|null }`) e roteia; a forma antiga
(`{ tabela: linha }` sem `{ table }`) continua sendo o INSERT cru.

**Desvio do plano, registrado no report do 019**: o plano dizia *"coluna nova numa
linha posterior é erro do chamador"*. Implementei `ALTER TABLE ADD COLUMN` em vez
disso. Motivo: o caso de uso do fswatch É esse — arquivo visto (`put` sem `size`),
depois medido (`put` com `size`). O `merge` do iodb tolera (a chave aparece); para a
paridade ser REAL, o adapter tem que tolerar também. O código está certo; o plano
subestimou o que "pareada" exigia.

## 2. A frente 6.3 — a reconstrução comparativa

**Pedido do usuário, refinado ao longo da sessão em quatro mensagens:**

- não fazer benchmarks além da reconstrução comparativa dos repos listados;
- saber o que tem em cada repo, e comparar iodb paged text vs baseline sqlite ao
  guardar os dados nos dois formatos;
- **separar scanning de tree do storage dos registros** — o scan deve ser IGUAL
  para os dois formatos;
- comparar os dois na construção do corpus, nos lookups e nas buscas dentro dele;
- *"não é bem um benchmark, é um uso comparativo. as duas engines rodam lado a lado
  e simplesmente registra os tempos de cada uma."*

### O que `fswatch/bench.js` faz

Por repositório (`~/iodb`, `~/utest`, `~/sprint-cli`, `~/soml`):

1. **Scan da árvore inteira, UMA vez.** `scanTree` faz a recursão usando o `describe`
   exportado do `fswatch.js` (o `lstat` + identidade `dev:ino`, com `path`). Esse
   mesmo `found` (Map) alimenta os dois stores. Tempo de scan reportado sozinho.
   *Sem poda* — `.git` e `node_modules` incluídos, porque a pergunta é "o que tem no
   repo". (O `fswatch.js` em produção poda; aqui não.)
2. **Construção do corpus, nos dois formatos, do mesmo `found`.** iodb: puts
   bufferizados, um flush no fim. sqlite: as mesmas entries dentro de UMA transação
   (`store.db.exec('BEGIN'/'COMMIT')` pelo handle exposto — sem isso o `bun:sqlite`
   faz fsync por linha e uma execução chegou a 112000ms para 22k entries).
3. **Lookups** dentro de cada corpus: por chave (`dev:ino`) e por path.
4. **Buscas** por predicado: `name ~ .js`, `kind = dir`.

Stores num `os.tmpdir()`, nunca num `.fswatch/` real.

### O que a reconstrução mostrou (soml, 24511 entries — UMA execução)

| fase                   | iodb     | sqlite   | estável? |
|------------------------|----------|----------|----------|
| scan (comum aos dois)  | ~2300 ms | —        | —        |
| construção do corpus   | ~5300 ms | ~370 ms  | **não** (~10x entre runs) |
| **corpus em disco**    | **7.5M** | **11.4M**| **sim** |
| lookup por chave (200) | 0.1 ms   | 1.0 ms   | sim     |
| lookup por path (200)  | ~690 ms  | ~370 ms  | não     |
| busca `name ~ .js`     | ~25 ms   | ~1.6 ms  | ~sim    |
| busca `kind = dir`     | ~4 ms    | ~1.2 ms  | ~sim    |

**O que se lê com honestidade:**

1. **iodb guarda menos** — `.dash` + derivados em ~66% do `.sqlite`, nos quatro
   repos, sem balançar. É o único número forte, e é a favor do formato texto.
2. **iodb constrói mais devagar** — o build bufferizado do `.dash` paginado + a
   manutenção do `mirror` (o espelho em RAM, workaround do defeito de leitura viva
   do sprint 017) custa mais que uma transação única. Quanto, esta execução não diz
   (varia 10x). Que é mais devagar, diz.
3. **iodb busca mais devagar em árvore grande** — `all().filter(...)` materializa as
   24k linhas do `mirror` a cada chamada. É exatamente o teto de RAM e o `find()`
   linear que as frentes 2 e 4 existem para remover.
4. **lookup por chave é empate** — a projeção chaveada e o índice por PK fazem a
   mesma coisa.

### Por que não tem teto no eval

`6.3.eval.js` afirma só sobre a ESTRUTURA da saída (os quatro repos rodaram, o scan
é destacado, as duas colunas têm número em cada fase). **Nenhum teto de tempo** — um
teto reintroduziria a moldura de benchmark que o usuário rejeitou explicitamente.

`ISSUES/001`. O `verify_tests` da 6.1 (e da 6.2) tem
`bun plans/6-fswatch/6.1.eval.js` — um `.eval.js` NÃO roda como script (`eval("cmd",
...)` é DSL de `sprint eval`, não JS). `sprint test` executa a string e quebra;
`sprint eval` interpreta e passa. **A evidência real nunca quebrou.**

**Desfiz o dano**: `git checkout plans/6-fswatch/6.1-*.md` — o frontmatter tinha
virado `state: evaluated`, `verify_confirmed: false`. 6.1 está de volta em 🔵.

**Convenção certa** (aplicada na 6.3 desde o início): `verify_tests` = só a suite
utest (`bun ../utest/utest.js …`). O `plans/N-front/N.F.eval.js` é descoberto pelo
NOME por `sprint eval N.F`, não entra em `verify_tests`. 6.1 e 6.2 violam isso e são
arquivo commitado — corrigir é sprint próprio.

### 3.2 `sprint close` e `sprint docs` crashavam `EISDIR`

`ISSUES/002`. O loop da raiz em `sprint-cli/cmds/docs-check.js:~173` não filtra
diretórios (o `walk()` recursivo filtra). Um diretório `.md` na raiz —
`ISSUES.md/`, que o usuário tinha criado — faz `readFileSync` nele e crasha.
Bloqueava `close` para 020 E 021.

**Conserto aplicado**: `ISSUES.md/` (diretório) virou `ISSUES/` (diretório, sem
`.md`) + `ISSUES.md` (arquivo, o kanban). O crash sumiu, `docs:check — ok`.
Conserto no `sprint` (uma linha, adicionar o guarda `isFile()`) fica registrado em
`ISSUES/002`.

## Regras do método — não esquecer

- **`sprint boot` PRIMEIRO**, devolvendo as provas de cada passo.
- Estado do workflow → SEMPRE `sprint`, nunca `git log`/`ls`/`grep`.
- Antes de codar: `sprint files --drift <arquivos>`. **FORA = sprint novo**, não
  scope creep. Nesta sessão isso apontou a frente 7 três vezes.
- **`sprint test` ≠ `sprint eval`.** `sprint test` roda os `verify_tests` literais;
  `sprint eval` interpreta a DSL dos `.eval.js`. NÃO rodar `sprint test` numa
  feature cujo `verify_tests` tenha um `.eval.js` (ver `ISSUES/001`).
- **🔵 é do humano.** O agente chega a 🟢 e para.
- **`sprint close` é do usuário** — ele encena só os arquivos do sprint, o commit é
  do humano.
- No utest: `checkException(fn)` é param do contexto, NÃO `check.checkException`.
- Achou problema fora do escopo? **Reporte, não conserte** — e agora tem onde:
  `ISSUES.md`.
