## TL;DR do que decidimos

A chave de um registro é `key = shortestPrefix( sha64(patch) XOR sha64(targetKey) )`
— o menor prefixo binário livre do hash. Isso **não precisa de lock**: depende só
do patch e do target. A coordenação que sobra é o `.index` (mapa de ocupação de
nomes) e o append serializado dos bytes.

A tríade `.dash` / `.index` / `.yaml` nasce junta com a entity, todas derivadas do
`.dash`, todas publicadas fora do lock, todas reconstruíveis.

## 1. A fórmula da chave

```
fullKey(patch) = sha64(patch) XOR sha64(targetKey)
key(patch)     = shortestPrefix(fullKey, bitmaps)   // menor prefixo binário livre
```

- **`targetKey` é a chave CURTA do objeto patcheado** (`"1a"`), não o hash. É o
  que `lookup()` procura. **Só existe chave curta** — `fullKey` é um intermediário
  efêmero do cálculo, não é armazenada nem exposta.
- **Objeto novo (sem patch): `targetKey = null`.** A fórmula degenera para
  `sha64(patch) XOR sha64(null)` — o comportamento de hoje para o primeiro
  registro.
- **Sem `seq`, sem salt.** A colisão de patch idêntico (mesmo `patch`, mesmo
  `target` → mesma `fullKey`) resolve pela **mecânica de level-up**: o primeiro
  pega `bits[0..L]`, o segundo encontra `bitmap[L]` ocupado e sobe para
  `bits[0..L+1]` (o próximo bit da mesma `fullKey`, livre). Dois registros de
  conteúdo idêntico → chaves distintas em níveis distintos, ambos prefixos
  válidos da mesma `fullKey`, ambos passam `verify()`.

### O que a fórmula dá "de graça"

Todo patch do objeto X carrega, embutido na chave, um prefixo de `sha64(Xkey)`.
`recoverPrevKeyHash(key, patch)` = `fromB64(key) XOR sha64(patch)` devolve esse
prefixo — **prova probabilística de pertencimento** (falso-positivo `2^-L`, cai
conforme a coleção cresce). Não é recuperação exata do id; é "esse patch pertence
ao target X?" verificável sem índice.

### Decisão A (não B) — por quê

`parent` = **target** (o objeto que recebe o patch), não `chainPrev` (o vizinho
temporal no log). A operação central do iodb é "adicionar um valor a um objeto de
forma rastreável" — não "reconstruir a história de um objeto". A cadeia-por-objeto
(cada patch aponta pro anterior do mesmo objeto) foi **descartada**: forçaria um
`lookup(objeto → último patch)` no caminho crítico da escrita, trazendo o `.index`
pra dentro do lock. Com A, o chamador já tem o `targetKey` na mão.

O "índice de patches de um objeto" vira **problema externo** — scan do log
filtrando por `recoverPrevKeyHash`, ou um índice reverso opcional (futuro / 2.4).

## 2. A tríade

```
entity/
  <name>.dash    ← o log. a verdade. append-only, hash chain. NÃO deriva de ninguém.
  <name>.index   ← o mapa de ocupação de nomes. deriva do .dash.
  <name>.yaml    ← a projeção. o estado reduzido. deriva do .dash.
```

- **Nasce junta** no `writeGenesis` / primeira escrita. `#0` (genesis) + `#1`
  (marca de projeção) no `.dash`; bitmaps com `#0`/`#1` já registrados + header no
  `.index`; projeção inicial no `.yaml`.
- **Todas reconstruíveis** do `.dash` via `syncFrom(0)`.

### Coordenação da tríade — LOCK POR ARQUIVO (decisão desta sessão)

**Um lockfile por arquivo mutável.** O nome do lock identifica qual arquivo está
reservado pra mutação:

```
<base>.<pid>.lock.dash     ← este processo está mutando o .dash
<base>.<pid>.lock.index    ← ... o .index
<base>.<pid>.lock.yaml     ← ... o .yaml
<base>.<pid>.lock.<outro>  ← qualquer arquivo futuro, mesma regra
```

**Protocolo: presence = held, ausência = livre, PID no NOME** (não no conteúdo —
diferente do `io-append.js` atual). O mutex é o **scan + recheck com desempate
determinístico por PID**, não o `wx`:

```
acquireLock(base, file):
  mine = `${base}.${pid}.lock.${file}`
  loop até deadline:
    holders = readdir(dir).filter(match `<basename>.*.lock.<file>`)
    live    = holders.filter(h => alive(pid_of(h)) && pid_of(h) !== pid)
    if live.length === 0:
      writeFileSync(mine, '', {flag:'wx'})       // wx no MEU caminho
      recheck holders; se surgiu um com pid MENOR → unlink(mine), re-loop
      return mine
    sweep dead holders (unlink)                  // kill(pid,0) falhou
  throw Lock timeout
```

Vantagem sobre PID-no-conteúdo: `readdir` já diz **quem** detém, sem abrir arquivo.
Custo: a janela entre "vi livre" e "criei o meu" precisa do recheck + desempate.

**Reserva pra mutação — cada arquivo, sua janela, na ordem `.dash` → `.index` →
`.yaml`:**

```
flush():
  fullKey = sha64(patch) XOR sha64(targetKey)
  key     = allocKey(fullKey)              ← SEM lock (bitmaps em memória)

  acquireLock(base, 'dash')                ← reserva o .dash
    syncFrom(delta); re-allocKey se o delta ocupou o prefixo
    appendFileSync(.dash, bytes)
    ts = ts do último registro apendado
  releaseLock('dash')

  acquireLock(base, 'index')               ← reserva o .index
    publishDerived(.index, bitmaps, ts)    ← read-ts/compare/write-tmp/rename
  releaseLock('index')                       INDIVISÍVEL sob este lock

  acquireLock(base, 'yaml')                ← reserva o .yaml
    publishDerived(.yaml, projection, ts)
  releaseLock('yaml')
```

Locks **independentes**, três aquisições curtas do mecanismo, ordem fixa evita
deadlock. Entre janelas cada lock está livre — outro processo entra, faz seu
append, publica seus derivados.

**Por que o publish precisa do lock (não só do rename atômico):** `publishDerived`
faz `read header → compare ts → write tmp → rename`. Sem lock, dois processos
podem ambos ler `existing_ts = T`, decidir publicar T+1 e T+2, e o de T+1 renomear
DEPOIS do de T+2 — perdeu a corrida do rename apesar do ts menor. O
`read-compare-write` não é atômico; o lock do arquivo o torna.

```
publishDerived(file, content, ts):        // roda DENTRO de acquireLock(base, <file>)
  existing_ts = readHeaderTs(file)
  if existing_ts != null and existing_ts >= ts: return   // já tem versão >=
  writeFileSync(file + '.<pid>.tmp', content)
  renameSync(tmp, file)
```

**O `ts` não é sincronizado por mecanismo especial** — é COPIADO do último registro
do `.dash` depois do unlock do `.dash`, e cada derivado carrega o seu no header
(`syncedAt=<ts>`). `nano()` já existe em `hash.js`.

### Contrato de validade dos derivados

**Um `.index` ou `.yaml` só é VÁLIDO no `ts` que carrega.** Desatualizado =
**incompleto, não inválido** — é uma verdade parcial, correta até `syncedAt`.

Para usar como verdade corrente: `syncFrom(syncedAt)` o delta do `.dash` primeiro.
- `get(id)` na projeção: se `projection.syncedAt < dash.lastTs` → `syncFrom` antes de responder.
- `lookup(id)` no `.index`: idem, ou aceita o resultado conservador (pode dizer "não existe" pra algo no delta não-sincronizado).
- `open()`: lê `syncedAt` de `.index` e `.yaml`, pega o **menor**, `syncFrom` daquele ponto, alinha os três.

Vale IGUAL pros dois derivados — mesmo contrato.

### `.out(fn)` / `ON('io:name', fn)` — fora da tríade

Callbacks de consequência disparam quando o writer processa o flush, **fora de
qualquer lock**, a qualquer momento, possivelmente atrasados ou em paralelo. Não
são parte da tríade — são efeito colateral observável. Já é assim no código
(io-engine e nutshell emitem depois do unlock).

### Consequências

- **Um processo pode morrer entre qualquer janela.** `.dash` tem a verdade;
  `.index`/`.yaml` faltando ou atrasados → `open()` reconstrói a partir do
  `syncedAt` que carregam.
- **`.index` e `.yaml` podem divergir entre si transitoriamente** (um em ts T,
  outro em T+3). Não é corrupção. `open()` pega o menor e `syncFrom` alinha.
- **A tríade "está junta" quando os três ts batem** — O(1) no `open()` (ler 3
  headers), não um scan.

### versionamento semântico nos cabeçalhos (decisão desta sessão)

`#0` passa a carregar `{_entity, _type, _v: "0.1.0", _format: "lrm-1"}`. `open()` lê
`_format`; se não reconhece, recomputa ou rejeita com mensagem clara.
**PENDENTE: dentro de 1.5 ou feature própria?** O `.index` já mexe no genesis, então
cabe aqui; mas é ortogonal o suficiente pra sair.

## 3. O `.index` — formato e papel

```
_v=0.1.0
_format=lrm-1
lastOffset=<byte até onde li o .dash>
syncedAt=<ts do registro em lastOffset>
1{"count":N,"bits":"<b64 do bitmap de 2 posições>"}
2{"count":M,"bits":"<b64 de 4 posições>"}
6{"count":K,"bits":"<b64 de 64 posições, 1 BigInt>"}
...
```

- **bitmap por nível**: nível `L` tem `2^L` posições, bit `i` ligado = prefixo
  binário `i` (comprimento `L`) em uso. Nível 6 = 64 bits = 1 BigInt. Nível 12 =
  512 bytes. Nível 24 (~16M registros) = ~4 MB somando todos os níveis.
- **`count` por nível**: ocupação. `closed` = `count === 2^L`. `lookup`/`allocKey`
  pulam níveis fechados. É a "forma da coleção" para 2.4.
- **`lastOffset`**: fast-open + árbitro de ordem do `saveIndex`.
- **SEM `lastKey`** (não está na fórmula). **SEM `seq`**. **SEM `lastKeyOf`**
  (decisão A).

### Papel mais amplo

O `.index` é **o alocador de nomes, persistido e consultável sem lock**. Uma
responsabilidade só: "quais prefixos binários já foram usados, por nível". Disso
derivam: `allocKey` (escrita), `lookup` (leitura), `levels()` (forma, pra 2.4),
`headOffset()` (fast-open). **Não** é catálogo de objetos, **não** é histórico,
**não** é projeção.

É o que faz o iodb deixar de ser "um log que eu releio inteiro toda vez" e virar
"um log com um catálogo".

## 4. `allocKey` e `lookup` — sem lock

### `lookup(id, { upto })` — DOIS MODOS (decisão ponto 8)

- **`id` é uma chave (id de objeto)** → match **exato**. "Esse id existe? em que
  nível?" Para dedup, `get`, resolução de `targetKey`.
- **`id` é um hash sha** → **maior match de prefixo**, a menos que `upto` (nível
  máximo) seja fornecido. Para `allocKey` (detectar clash em qualquer nível ≤ L).

```
lookup(bits, uptoLevel):
  L = uptoLevel ?? bits.length
  for l in 1..L:
    pos = parseInt(bits[0..l], 2)
    if bitmap[l].bit(pos): return { exists: true, level: l }
  return { exists: false, level: null }
```

**Custo: O(L) = O(log₆₄ n) testes de bit em memória.** Dezenas de ns, sub-µs até
10⁹ registros. Sem disco, sem lock.

### `allocKey(fullKey)` — substitui `shortestPrefix(fullKey, prefixSet)`

É um `lookup` no modo hash que continua subindo `L` até achar um prefixo onde
nenhum nível `l ≤ L` colide E `bitmap[L]` não tem `fullKey[0..L]`. Palpite inicial
de `L`: `positionToKeyLength(count)` do `.index` (atrasado = `L` baixo demais = mais
iterações, nunca incorreto — ponto 10). Sem lock, sem Set reconstruído.

### `saveIndex` / `saveYaml` — quando (decisão ponto 5)

**Imediatamente depois do unlock**, na ordem `.dash` → `.index` → `.yaml`. Cada um
via `publishDerived` (§2): `tmp.<pid>` + `renameSync` atômico + árbitro de
`ts`/`lastOffset` — um publish só sobrescreve outro de um ponto `>=`. Nunca
sobrescreve versão mais nova, sem lock. `flush()` não espera o rename (microtask/
Promise-chain; as escritas do MESMO processo serializam entre si por fila, não
lock).

Se o processo morre entre o append e o publish de qualquer derivado: o próximo
`open()` lê o `ts`/`lastOffset` do header de cada derivado, pega o menor, e
`syncFrom` o delta pra alinhar os três. **Teste explícito necessário** (mata o
processo depois do append, antes do `saveIndex`/`saveYaml`; `open()` recupera).

## 6. `verify()` no domínio novo (darkspot — ponto 3)

`verify` obtém o `target` de cada registro por `recoverPrevKeyHash(key, payload)` →
devolve `sha64(target)` **mascarado nos bits do prefixo** (a chave é curta). Então
`verify` **não recupera o `targetKey` exato** — recupera um prefixo de
`sha64(target)`.

Para validar, `verify` compara esse prefixo contra `sha64` de cada candidato a
target que conhece (as chaves já vistas no scan). **O(n²) no pior caso, ou O(n)** se
mantiver um mapa `sha64(key)[0..L] → key` durante o scan. É trabalho real da
implementação de `verify`. Alternativa se ficar caro: `verify` valida só unicidade
de chave (scan) e abre mão do check de prefixo-do-hash — mas isso enfraquece a
prova.
