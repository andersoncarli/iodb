# [4.1] reorganizar-arvore-src-adapters

## Objetivo

Sair de uma raiz plana com ~38 arquivos `.js` misturando nucleo e adapters de
storage, e organizar em `src/` (nucleo: db, node, hash, io-engine, io-append
via `src/adapters/`, command-engine, find-root, collection-base) e
`src/adapters/` (os 21 adapters numerados: file, blob, folder, dash, jsonl,
yaml, json, env, sqlite, node, transition). `nutshell/` fica intocado (e outro
engine, nao um adapter deste projeto) — so os `import`/`require` que apontavam
para arquivos movidos foram corrigidos.

## Classificacao aplicada

**`src/` (nucleo):** db.js, db.t.js, db.dx.t.js, db.io.t.js, db-factory.js,
db-factory.t.js, node.js, node.t.js, node-core.js, hash.js, hash.t.js,
command-engine.js, io-engine.js, io-engine.bench.js,
io-engine.concurrency.test.js, io-engine.matrix.test.js, io-engine.test.js,
find-root.js, collection-base.js.

**`src/adapters/` (adapters de storage):** 01-file.js, 01-file.lines.js,
01-lines.js, 02-blob.js, 02-file.blob.js, 0-folder.js, 10-dash.js,
10-dash.md, 10-dash.t.js, 15-jsonl.js, 15-jsonl.t.js, 20-yaml.js,
20-yaml.t.js, 30-json.js, 30-json.t.js, 40-env.js, 50-sqlite.js,
50-sqlite.t.js, 60-node.js, 60-transition.js, io-append.js.
(`60-node.t.js` nao existe no repo — nao ha o que mover.)

**Ficou onde estava:** tudo em `nutshell/`, `docs/`, `plans/`, `sprints/`,
`.sprint/`, README.md, AGENTS.md, CHANGELOG.md, STATUS.md, TEST.boot.js,
sprint-issue-iodb.md. Nao apareceu nenhum `.js` de raiz fora das duas listas
acordadas — nao houve caso ambiguo de classificacao.

## O que foi feito

1. `git mv` arquivo por arquivo (preserva historico) para `src/` e
   `src/adapters/` conforme a classificacao acima.
2. Imports corrigidos:
   - Dentro de `src/*.js`: `../utils/...` -> `../../utils/...` (um nivel a
     mais de profundidade); referencias cruzadas para adapters que moveram
     (`./60-node.js`, `./50-sqlite.js`, `./30-json.js`, `./40-env.js`,
     `./60-transition.js`) -> `./adapters/<arquivo>`.
   - `src/db-factory.js`: `ADAPTERS_PATH` (usado pelo scan dinamico de
     adapters por `readdirSync` + `await import`) passou de `__dirname` para
     `join(__dirname, 'adapters')`, e o `import(\`./${entry}\`)` passou a
     `import(\`./adapters/${entry}\`)` — sem isso o factory pararia de achar
     os adapters em runtime.
   - Dentro de `src/adapters/*.js`: `./collection-base.js` -> `../collection-base.js`
     (collection-base ficou em `src/`, nao em `src/adapters/`).
   - `src/io-engine.js`: `./io-append.js` -> `./adapters/io-append.js`.
   - `nutshell/io-hash.js` (`../hash.js` -> `../src/hash.js`) e
     `nutshell/io-nutshell.js` (`../io-append.js` -> `../src/adapters/io-append.js`)
     — nutshell importa arquivos do core que moveram; nutshell em si nao
     mudou de lugar.
   - `plans/2-pages/2.3.probe.js` (sprint fechado 2.3): `import` e a
     construcao dinamica de `ENGINE` apontavam para `../../io-engine.js` na
     raiz — corrigido para `../../src/io-engine.js`.
   - `plans/2-pages/2.3.eval.js` e `plans/1-core/1.1.eval.js` (sprints
     fechados 2.3 e 1.1): strings de shell (`grep`/`sed`/`bun -e`) que essas
     demonstracoes rodam ao vivo apontavam para `io-engine.js`, `io-append.js`
     e `./db.js` na raiz — corrigidas para `src/io-engine.js`,
     `src/adapters/io-append.js` e `./src/db.js` para as demonstracoes
     continuarem rodando sob `sprint eval --sweep`. So os caminhos executados
     foram tocados; a prosa/comentarios explicativos desses arquivos de
     sprints ja fechados nao foram reescritos.
   - `package.json`: `"main": "db.js"` -> `"main": "src/db.js"`.
3. Nao mexidos, por decisao deliberada (nao sao paths executados, sao
   documentacao/log): o bloco de codigo de exemplo em
   `plans/1-core/1.2-saveindex-corrompe-....md` (markdown ilustrativo de um
   sprint fechado) e `.utest/STATE.yaml` (cache/log gerado pelo utest, que se
   auto-corrige no proximo scan). `TEST.yaml` usa globs (`**/*.t.js` etc.) e
   nao precisou de mudanca. `.sprint/config.json` ja usa
   `bun utest/utest.js .` (relativo, sem depender de caminho de arquivo
   movido).

A numeracao (`0-`, `01-`, `02-`, `10-`, `15-`, `20-`, `30-`, `40-`, `50-`,
`60-`) so existia para o `readdirSync` + `sort` de `db-factory.js` carregar
os adapters em ordem determinada. O usuario confirmou: manter a ordem, mas
via carregamento explicito num index, nao via nome de arquivo.

### `src/adapters/index.js` (novo)

Import explicito de cada adapter, na mesma ordem que os prefixos indicavam:
`folder, file, file.lines, lines, blob, file.blob, dash, jsonl, yaml, json,
env` num array `ADAPTERS` de `{ handle, module }` (o `handle` e o mesmo texto
que antes vinha do nome do arquivo sem prefixo); `sqlite`, `NodeAdapter`
(de `node-adapter.js`) e `TransitionBus` exportados a parte, replicando
exatamente a forma como `db-factory.js` ja os consumia individualmente
(sqlite fora do loop generico, node/transition por import nomeado direto).

### `src/db-factory.js` atualizado

Removido o `readdirSync(ADAPTERS_PATH)` + regex `^\d+-` + `sort` que dependia
do prefixo numerico para ordem. Passou a iterar `ADAPTERS` (import de
`./adapters/index.js`) — mesma logica de resolucao de factory por modulo
(`${Cap}Collection` ?? `${Cap}Factory` ?? `module[handle]` ?? `module.default`),
so que a ordem e a lista vem do index, nao do filesystem. `BACKENDS['sqlite']`
passou a vir de `sqlite.default` (re-exportado pelo index) em vez de
`await import('./adapters/50-sqlite.js')`. `NodeAdapter` tambem importado do
index em vez de `./adapters/60-node.js`.

### Outros imports corrigidos (apontavam para nomes com prefixo)

`src/node-core.js` (`./adapters/60-transition.js` -> `./adapters/transition.js`),
`src/node.t.js` (`./adapters/30-json.js` -> `./adapters/json.js`,
`./adapters/40-env.js` -> `./adapters/env.js`), e dentro do proprio
`src/adapters/`: `folder.js` (`./60-node.js` -> `./node-adapter.js`),
`yaml.t.js`, `dash.t.js`, `json.t.js`, `sqlite.t.js`, `jsonl.t.js` (imports
relativos ao proprio arquivo de-prefixado).

`command-engine.js` tem seu proprio `loadAdapters()` — investigado e
confirmado que e um conceito diferente (adapters de *skills*, carregados de
outro caminho), nao os adapters de storage de `src/adapters/`; nao precisou
de mudanca.
