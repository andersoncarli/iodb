# [2.4] Indice plugavel

Transforma o `.index` — hoje write-only — num CONTRATO de indice real chave->offset,
com implementacoes plugaveis (text-pages, sqlite, e o que vier depois) atras da mesma
interface, destravando fast-open e leitura por range em qualquer uma delas.

## Objetivo

Transformar o `.index` de artefato **write-only** em indice real — chave->offset — sem
prender o `io-engine.js` a UM algoritmo. O spike da sprint 024 (texto-vs-sqlite) mostrou
dois vencedores em criterios diferentes: sqlite ganha fast-open e range por ordens de
grandeza; text-pages preserva `cat`/`grep` e roda em Node E Bun. Um contrato modular deixa
as duas coexistirem como plugins, escolhidas por config, em vez de forcar uma decisao
unica e definitiva no formato do arquivo.

### O contrato (implementado — src/index-contract.js, src/index-registry.js)

```js
// toda implementacao de indice e uma factory (file, opts) => objeto com esta forma
IndexImpl(file, opts) => ({
  open(),                    // le/cria o arquivo de indice; idempotente
  close(),                   // flush final + libera recursos (fd, conexao)
  get(key)      => offset | undefined,
  put(key, offset),          // upsert
  del(key),                  // tombstone ou remocao real, a criterio da implementacao
  range(lo, hi) => Iterable<[key, offset]>,  // ordenado por chave
  rebuild(fromOffset, records),  // reconstroi o estado a partir do .dash
})
```

`io-engine.js` fala so com essa forma (ainda nao fala — ver "Fora de escopo" no report do
sprint 024). A escolha de QUAL implementacao usar (`text-pages` default, `sqlite` opt-in) e
config no `open()` do store, resolvida por um registro nome -> factory:

```js
// src/index-registry.js
const impls = new Map()
export function registerIndex(name, factory) { impls.set(name, factory) }
export function createIndex(name, file, opts) {
  const factory = impls.get(name)
  if (!factory) throw new Error(`[index] implementacao desconhecida: ${name}`)
  return factory(file, opts)
}
```

Uma implementacao nova (`registerIndex('minha-btree', MinhaBtree)`) nunca edita
`io-engine.js` — so se registra antes do primeiro `open()`.

**As duas implementacoes de referencia:**

- **`text-pages`** (default, `src/index-textpages.js`) — hoje um `Map` persistido em
  linhas JSON; prova o contrato e preserva `cat`/`grep`/Node+Bun. O formato de pagina real
  (4096 bytes, header versionado, slotted page, checksum por pagina, freelist) descrito no
  restante deste documento e um incremento SEGUINTE sobre este mesmo arquivo — o contrato
  nao muda quando ele chegar, so a forma como `get`/`put`/`range` sao resolvidos por baixo.
  Custo conhecido: `put()` reescreve o arquivo inteiro por chamada (O(n) por escrita).
- **`sqlite`** (opt-in, `SqliteIndex` em `src/adapters/sqlite.js`) — tabela dedicada
  `idx(key TEXT PRIMARY KEY, offset INTEGER)`; auto-registra `'sqlite'` ao ser importado
  (isola `bun:sqlite`, que e Bun-only, de quem nunca pediu sqlite).

**O que NAO fica plugavel:** o `.dash` (log append-only) continua unico e obrigatorio — o
contrato e so para o `.index` derivado. `rebuild` sempre parte do `.dash`; nenhuma
implementacao de indice e fonte de verdade.

**Verificacao:** `src/index-registry.t.js` roda a mesma bateria contra as duas
implementacoes (round-trip, del, upsert, range, rebuild, close/reopen) mais um teste de
concordancia direta; `plans/2-pagedtext/2.4.probe.js` prova que uma terceira implementacao
se registra sem tocar `io-engine.js` nem os testes existentes. Detalhe completo:
[sprints/024-indice-paginado-4k-spike.report.md](../../sprints/024-indice-paginado-4k-spike.report.md).

## Historico da decisao — de "escolher uma" para "contrato plugavel"

**2026-09-10 — primeira decisao, sem medicao.** O spike declarado (B-tree propria em
paginas de texto vs `bun:sqlite`) foi resolvido a favor de **paginas de texto proprias**,
sem rodar a medicao, com base nos 11 documentos de `pagedtext/docs/`: `cat`/`grep`
continuam funcionando (sqlite e binario opaco); o engine roda em Node E Bun, `bun:sqlite`
so existe no Bun; o `.dash` ja e o write-ahead log, entao o WAL do sqlite nao agrega.

**2026-09-11 — numero rodado mesmo assim (sprint 024).**
`plans/2-pagedtext/2.4.spike.js` mediu scan/replay (o custo de hoje, sem indice real)
contra `bun:sqlite` em 20k/100k. Sqlite venceu fast-open (262ms -> 0.46ms em 100k) e
range (40ms -> 0.8ms) por ordens de grandeza — exatamente os dois criterios que este
documento lista. Apresentado o numero, a decisao inicial foi mantida standalone (ver
[sprints/024-indice-paginado-4k-spike.report.md](../../sprints/024-indice-paginado-4k-spike.report.md)).

**2026-09-11 — segunda decisao, o contrato.** Em vez de escolher UMA implementacao para
sempre, o formato do `.index` deixa de ser a decisao: vira uma INTERFACE, e as duas
abordagens entram como implementacoes plugaveis. Ninguem perde: quem quer `cat`/`grep` e
Node puro usa text-pages; quem quer fast-open/range imediato e ja tem Bun usa sqlite. A
B-tree propria (text-pages) continua sendo a implementacao DEFAULT — o motivo de
09-10 (portabilidade, legibilidade) nao mudou — mas deixa de ser a UNICA.

## Achado (4.1, nao consertado — fora de escopo do bench): `shortestPrefix` e O(n) por chamada

Perfilando o seeding do bench (`bun --cpu-prof`) contra 20k escritas em lote, `shortestPrefix`
(hash.js:114-124) domina o self-time (~15% do total). A funcao testa `bitsSet.has(p)` para
`n = 1..64`, fatiando `binaryKey.slice(0, n)` a cada tentativa — uma string nova por
tentativa, `n` tentativas por chamada. Como `bitsSet` (`idx.prefixSet`) cresce com o numero
de registros, colisoes em prefixos curtos ficam mais frequentes e o `n` medio cresce com o
tamanho do store: o custo por escrita nao e O(1), e cresce com o log inteiro, independente
de qualquer coisa que `4.2`/`4.3` consertem na secao critica.

Nao e o gargalo que este front ataca (que e a secao critica: `saveIndex`/`flushYaml`
reescrevendo arquivos inteiros dentro do lock) — e um custo de PRE-COMPUTO, fora do lock.
Mas e relevante para `2.4`: o indice paginado ja vai carregar `prefixSet`/estrutura radix
como estado persistente; se o layout de pagina expuser os prefixos por nivel (trie), a
alocacao de prefixo pode consultar a pagina certa em vez de testar `n` bits sequencialmente
contra um `Set` que so cresce. Vale medir junto do spike desta feature, nao antes.
