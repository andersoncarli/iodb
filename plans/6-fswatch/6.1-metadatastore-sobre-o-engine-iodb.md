# [6.1] MetadataStore sobre o engine iodb

O fswatch para de usar SQLite. A persistencia de metadados passa a ser um store `iodb`
chaveado por `dev:ino`, e o consumidor nao fica sabendo.

## Objetivo

Esta e a feature que da nome a frente. Tudo o mais aqui — o acoplamento (6.2), as medidas
(6.3), a nota sobre o split (6.4) — e consequencia dela.

O achado que a torna barata: a persistencia inteira do fswatch mora numa fabrica de 65
linhas, e a projecao chaveada do `iodb` responde exatamente as quatro operacoes que ela
exporta. A troca e uma substituicao de corpo, com a assinatura preservada.

A forma:

```js
import IO, { merge } from '../src/io-engine.js'

const MetadataStore = base => {
  const io = IO(base, { reduce: merge, initial: {}, pageSize: 4096 })
  io.open()
  const put = e => io.in({ [e.id]: normalize(e) })
  const remove = id => io.in({ [id]: null })
  const all = () => Object.values(io.get('#1'))
  const close = () => io.close()
  return { io, put, remove, all, close }
}
```

O `pageSize: 4096` nao e enfeite: e o que mantem a projecao FORA da RAM, que e a
propriedade que a frente 2 construiu e que um baseline de milhares de entradas precisa.

## Onde isso pode dar errado

Dois riscos, e eles sao de naturezas opostas.

O **merge raso** e silencioso. Ele nao quebra teste nenhum hoje porque nenhum teste cobre o
flip dir<->file. O SQLite apagava a linha da outra tabela; o `merge` funde. A mitigacao e
cobertura nova, e ela e barata.

O **fsync por registro** e ruidoso e pode inviabilizar a escrita como ela esta. Ele nao e
bug: e o preco da durabilidade que o `iodb` cobra e o `bun:sqlite` nao cobrava. A saida
tecnica existe e esta no engine (`{ flush: 0 }` mais um `flush()` no fim), mas ela e uma
troca de durabilidade por velocidade DURANTE A VARREDURA, e uma troca dessas se escreve
antes, nao se descobre depois. Se o numero medido disser que a varredura ficou inviavel
sem o batch, o batch entra com a decisao registrada aqui.

## O que fica de fora

O `db:` na API publica sai e nao volta disfarcado de `io:`. As tres lacunas do README do
fswatch (o `baseline` vs `baselineFirst`, o `content_changed` que nunca sai, o `exclude`
que nao poda a varredura) sao bugs reais e nao entram nesta feature — estao registradas no
`_front.md`.
