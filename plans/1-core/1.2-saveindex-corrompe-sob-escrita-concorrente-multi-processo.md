# [1.2] saveIndex corrompe sob escrita concorrente multi-processo

## Objetivo

Achado de homologação vindo de `~/utest` (feature 8.1 `ledger.js`), que expôs `iodb` a
concorrência real (múltiplos processos `bun` escrevendo no mesmo `IO()`). **Corrigido no
sprint 002** — ver § Correção. O registro do achado abaixo fica como histórico do porquê.

## O que foi observado

8 processos concorrentes, cada um abrindo `IO(mesmoPath, {...})` e fazendo 30 `.in()`
writes, sem qualquer stagger:

- **9 de 10 execuções corromperam** (registros ausentes do log final).
- Perda média de **~81 registros de 242 esperados** (8×30 + 2 genesis) por rodada
  corrompida.
- Erro observado, quando propagado:
  ```
  ENOENT: no such file or directory, rename '<path>/ledger.index.tmp' -> '<path>/ledger.index'
      at saveIndex (io-engine.js:119:30)
      at flush (io-engine.js:252:9)      # dentro do lock
      -- ou --
      at open (io-engine.js:330:11)      # SEM lock
  ```
- **`verify()` continua `{valid: true}`** mesmo com a perda — a cadeia do que sobrou é
  íntegra, só não há como saber pela API que algo foi perdido.

## Causa raiz

`saveIndex()` (linhas 110-120):

```js
function saveIndex() {
  if (!f.index) return
  let out = `lastKey=${idx.lastKey || ''}\nlastOffset=${lastOffset}\n`
  // ...
  const tmp = f.index + '.tmp'
  writeFileSync(tmp, out); renameSync(tmp, f.index)
}
```

`tmp` é um nome FIXO, compartilhado entre todos os processos que abrem o mesmo `base`.
Compare com o protocolo de lock do `.yaml` (linha 37): `` `${f.yaml}.${process.pid}` `` —
sufixado por PID, exclusivo por processo.

Dois call sites expõem a colisão:

1. **`open()`, linha 319-332** — o ramo `else` (dash existe, projeta a partir do zero):
   ```js
   syncFrom(0)
   if (!existsSync(f.yaml)) {
     const tmp = f.yaml + '.tmp'
     writeFileSync(tmp, stringify(projection, ...))
     renameSync(tmp, f.yaml)
     saveIndex()          // <- SEM acquireLock() antes
   }
   ```
   Roda inteiro fora de qualquer lock. Se `f.yaml` está ausente porque outro processo
   está no meio do próprio `flush()` (renomeou `.yaml`→`.yaml.<pid>`), múltiplos
   processos entram nesse `if` ao mesmo tempo e todos chamam `saveIndex()`
   concorrentemente — mesmo `.index.tmp`.

2. **`flush()`, linha 252** — está DENTRO da seção com `acquireLock()` (linha 215), mas
   o lock protege o `.yaml`/dados principais, não isola o `.index.tmp` de um `saveIndex()`
   concorrente vindo do ramo 1 (que não usa lock nenhum). O `.tmp` compartilhado é o ponto
   de falha: processo A escreve `.tmp`, processo B (ramo 1, sem lock) sobrescreve o mesmo
   `.tmp`, processo A tenta `renameSync` um arquivo que já não tem o conteúdo que A
   escreveu (ou já foi movido por B) → `ENOENT` ou índice corrompido silenciosamente.

## Reprodutor mínimo

```js
// N processos rodando isto concorrentemente contra o MESMO path:
import IO, { append } from './io-engine.js'
const io = IO('/tmp/algum-path/LOG', { reduce: append, initial: [], format: 'jsonl' })
io.open({ _entity: 'x' })
for (let i = 0; i < 30; i++) io.in({ i })
```

Rodar 8+ instâncias desse script em paralelo (`&` no shell, ou `Promise.all` de
`Bun.spawn`) contra o mesmo diretório reproduz a corrupção em minutos — taxa observada
~90% com 8 processos / 30 writes cada.

## Impacto

Qualquer consumidor de `iodb` com escrita concorrente real — múltiplos processos ou
workers escrevendo no MESMO `IO()` base — está exposto a perda silenciosa de registros.
`verify()` não sinaliza isso (só audita o que sobrou). Só a exceção na hora do crash
denuncia, e só se o caller não a engolir.

O `~/utest/ledger.js` (feature 8.1) documenta essa ressalva e deixa o erro subir
naturalmente para quem chama — não tenta mascarar nem reimplementar o locking.

## Correção (sprint 002)

1. **`saveIndex()` — temp por-PID.** `const tmp = \`${f.index}.${process.pid}.tmp\`` no
   lugar do nome fixo `f.index + '.tmp'`. Cada processo escreve o próprio temp privado e
   faz `renameSync` atômico — sem colisão na janela write→rename. Mesmo protocolo que o
   lock de `.yaml` já usava.
2. **`open()`, ramo `else` — `saveIndex()` agora sob lock.** O bloco que reconstrói
   `f.yaml` quando ele está transitoriamente ausente (outro processo tem o lock) passou a
   `acquireLock(f)` antes de escrever o yaml + `saveIndex()`, com release por
   `renameSync(myLock, f.yaml)` / `unlinkSync(myLock)` e restauração do lock no `catch`.
3. **`flush()`, ramo não-centésimo — `saveIndex()` movido para dentro da janela do lock**
   (antes rodava depois do `renameSync(myLock, f.yaml)` que já solta o lock).

Reprodutor: `io-engine.concurrency.test.js` — 8 processos `bun` reais × 30 writes cada no
mesmo `IO()`, genesis semeado. Antes: `ENOENT` em ~90% das rodadas + perda silenciosa
(114–211 de 240 registros). Depois: 10/10 limpo, `verify().valid === true`, 240/240.

## Fora de escopo (bug distinto)

Sem semear genesis, 8 processos disputando o **primeiro** write ainda perdem ~10% dos
registros — a eleição de genesis em `open()` (`wx` exclusive-create + espera do perdedor)
sai da espera assim que `f.dash` tem tamanho > 0, o que pode ser entre a linha `#0` e a
`#1` de `writeGenesis()` (dois `appendFileSync` separados). Isso é uma feature nova, não
scope creep de 1.2.
